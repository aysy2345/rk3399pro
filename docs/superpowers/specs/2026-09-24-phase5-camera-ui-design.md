# Phase 5 摄像头、工作线程与桌面界面设计

## 1 目标与范围

Phase 5 在现有算法核心、原子人脸库、Fake 后端和 ONNX 后端之上，完成可运行的 PyQt5 桌面应用。应用使用 USB UVC 摄像头，支持实时 1:N 人脸识别、添加成员和成员管理。

本阶段默认使用 ONNX 后端完成真实运行，自动化测试使用 Fake 后端。RKNN 转换和板端 NPU 后端属于 Phase 6 与 Phase 7，不在本阶段实现。活体检测、考勤报表、云端同步和远程网页管理也不在本阶段范围内。

## 2 已确认的交互决策

- 主界面采用上下分区：上方为横向视频画面，下方为操作区和识别结果。
- 主窗口默认最大化，保留最小化、最大化和关闭按钮。
- 程序启动后处于待机状态，用户点击“开始识别”后才打开摄像头和推理后端。
- 添加成员使用“基本信息 → 采集样本 → 确认保存”三步向导。
- 添加成员时暂停实时识别，由登记流程独占摄像头；退出后恢复进入登记前的运行状态。
- 登记过程自动采集 15 个有效样本，并引导正视、左转和右转。
- 成员管理使用可搜索表格，行内提供编辑、重新采集和删除操作。
- Fake 与 ONNX 后端可切换；测试默认 Fake，真实运行默认 ONNX。

## 3 总体架构

应用采用分层结构和一个摄像头/推理工作线程。

    PyQt5 主线程
    ├─ MainWindow：状态展示、用户操作和窗口生命周期
    ├─ EnrollmentWizard：三步登记流程
    └─ MemberManagementDialog：成员搜索与管理
              │ Qt 信号/槽
              ▼
    RecognitionWorker（QThread 中运行）
    ├─ OpenCVCamera：USB 摄像头唯一所有者
    ├─ FaceDetector：Fake 或 RetinaFace ONNX
    ├─ FaceEmbedder：Fake 或 MobileFaceNet ONNX
    ├─ 对齐、质量检查、匹配与稳定器
    └─ MemberRepository 快照刷新
              │
              ▼
    FaceStore：members.json + embeddings.npy

界面主线程只创建控件、响应操作和显示结果，不执行摄像头读取或模型推理。工作线程独占摄像头，通过 Qt 信号发送复制后的预览帧、识别结果、状态和错误，不直接访问控件。

## 4 应用状态

主窗口维护以下互斥状态：

| 状态 | 行为 |
|------|------|
| 待机 | 不占用摄像头，可添加或管理成员 |
| 识别中 | 显示实时预览和稳定后的身份结果，可停止识别 |
| 成员登记中 | 暂停身份匹配，登记向导独占摄像头 |
| 错误 | 显示具体错误和可用的重试或返回操作 |

状态转换由应用控制器统一完成，控件不得各自维护重复状态。重复点击开始、停止或关闭登记窗口必须保持幂等。

## 5 摄像头与最新帧策略

`OpenCVCamera` 封装 `cv2.VideoCapture` 的打开、读取和释放。摄像头只能由工作线程访问。

工作线程循环读取一帧，先发送预览，再根据当前模式决定是否执行识别或登记采样。系统不建立无界帧队列；推理速度低于摄像头帧率时直接继续读取最新画面，避免旧帧积压导致延迟持续增长。

预览发送频率和推理频率允许分开配置。停止识别、退出登记或关闭程序时，控制器通知工作线程退出循环，等待线程结束后释放摄像头。摄像头读取失败时执行有限次数重试，仍失败则发出可恢复错误并回到错误状态。

## 6 实时识别流程

1. 用户点击“开始识别”。
2. 工作线程加载所选后端、打开摄像头并加载人脸库快照。
3. 检测器返回人脸框、置信度和五点关键点。
4. 系统对齐人脸，提取归一化特征并进行余弦匹配。
5. 稳定器按现有“5 帧至少 3 帧一致”规则确认结果。
6. 主界面绘制人脸框、姓名和相似度；低于阈值时只显示“陌生人”。

成员库为空时仍可显示预览和人脸框，但所有身份结果均为陌生人。成员数据发生有效变更后，工作线程以新快照替换旧快照，无需重启。

## 7 主界面

主窗口默认最大化运行：

- 上方视频区保持画面纵横比，多余区域使用中性色填充。
- 下方显示当前身份、相似度、运行状态、人脸库人数和错误提示。
- 提供“开始识别”“停止识别”“添加成员”“成员管理”四个主要按钮。
- 按钮启用状态完全由应用状态决定。

模型缺失、摄像头不可用、人脸库损坏等错误必须展示面向用户的说明，日志中保留技术细节。可恢复错误显示“重试”，不可安全写入的人脸库错误禁止成员修改操作。

## 8 添加成员向导

### 8.1 基本信息

用户输入唯一成员编号和姓名。编号去除首尾空白后不能为空且不能重复；姓名不能为空。同名不同编号允许保存，但需要给出提示。成员编号创建后不可修改。

### 8.2 自动采集

向导显示实时画面、当前姿态提示、有效样本数和目标样本数。只有同时满足以下条件的帧才计数：

- 画面中恰好一张人脸；
- 人脸尺寸达到配置门槛；
- 清晰度达到配置门槛；
- 姿态符合当前正视、左转或右转提示；
- 与上一次采集达到最小时间间隔；
- 与已有样本不存在明显重复。

默认目标为 15 个有效样本。界面说明未计数原因，但普通质量不足不作为程序错误。

### 8.3 确认保存

系统聚合有效特征并展示成员信息和采集摘要。只有用户确认后才调用原子人脸库写入。取消、关闭、特征聚合失败或保存失败都不得留下半成品成员；保存成功后刷新内存快照并恢复登记前的识别状态。

## 9 成员管理

成员管理窗口使用表格展示成员编号、姓名、样本状态和更新时间，支持按编号或姓名即时过滤。

- 编辑：只允许修改姓名等可变资料，成员编号保持不变。
- 重新采集：复用登记采集步骤；新模板保存成功后才原子替换旧模板。
- 删除：二次确认后同时删除成员元数据和对应特征。
- 刷新：操作成功后通知识别线程加载新快照。

任何取消或失败都保留原有成员和特征。界面操作不得直接修改 JSON 或 NPY 文件。

## 10 后端与配置

应用启动层根据配置创建后端：

- `fake`：用于单元测试、Qt 无界面测试和不带模型的演示。
- `onnx`：使用现有 RetinaFace 与 MobileFaceNet ONNX 适配器，作为 Phase 5 真实运行默认值。

现有 `AppConfig` 扩展后端类型、目标帧率、清晰度门槛和最小采样间隔。命令行允许覆盖配置文件路径、后端和摄像头编号，其他参数继续由 JSON 配置管理。示例配置中的模型后缀在 Phase 5 改为 ONNX；RKNN 路径将在后续板端配置中单独维护。

## 11 错误模型与资源释放

工作线程把异常转换为包含错误类别、用户提示和是否可重试的信息，再通过 Qt 信号交给主线程。至少区分：

- 摄像头打开失败或读取中断；
- 模型文件缺失、加载失败或输出无效；
- 人脸库读取或一致性校验失败；
- 成员保存失败；
- 未预期的工作线程异常。

关闭窗口时先禁止新操作，再请求工作线程停止并等待有限时间。正常路径必须释放摄像头；超过等待时间时记录错误并阻止后台线程继续访问已销毁的控件。

## 12 测试与验收

### 12.1 自动化测试

- 摄像头封装：打开失败、读取失败、重试和释放。
- 工作线程：启动/停止幂等、模式切换、最新帧策略、错误信号和快照刷新。
- 主窗口：四种状态对应的按钮和提示。
- 登记向导：校验、自动采样、取消不落盘、成功保存和失败回滚。
- 成员管理：搜索、编辑、重新采集原子替换和删除确认。
- Fake 集成：无摄像头和模型时跑通完整 UI 流程。
- ONNX 回归：继续验证真实模型的输入输出和匹配链路。

Qt 测试使用离屏平台插件运行，不依赖显示器。涉及摄像头的自动测试注入 Fake Camera，不访问真实设备。

### 12.2 人工验收

- 正常启动和停止识别；
- 摄像头不存在、运行中断开和重新重试；
- 已登记人员、陌生人和多人画面；
- 添加、取消添加、编辑、重新采集和删除；
- 关闭窗口后摄像头可被其他程序再次打开；
- 界面持续响应，视频延迟不随运行时间增长。

## 13 完成标准

Phase 5 完成时，主机环境应能通过 Fake 后端自动测试，并能用 ONNX 后端和 USB 摄像头完成真实识别及成员管理。全部新增测试和现有 28 项测试通过，配置示例与运行文档同步更新，且不引入 RKNN 或板端专属依赖。
