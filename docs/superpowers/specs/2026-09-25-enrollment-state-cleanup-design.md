# 登记结束后识别状态清理设计

## 背景

用户完成成员登记后再次点击“开始识别”，界面状态显示“识别中”、实时摄像头画面正常，但结果一直停留在“尚未开始识别”。

真实 ONNX 诊断已经排除模型与阈值问题：截图中检测到 1 张人脸，检测置信度为 0.996，与已登记模板的相似度为 0.9314，高于 0.6 的识别阈值。

根因是从待机状态开始登记时，登记完成会停止工作线程，但没有调用线程宿主的 `cancel_enrollment`。宿主中的 `_pending_enrollment` 因此保留旧会话；下一次启动识别线程时，旧会话被重新注入，新线程实际继续执行登记分支，无法发送识别结果。

## 修复方案

在 `AppController.cancel_enrollment` 中统一执行登记状态清理：

1. 只要当前状态为 `ENROLLING`，先调用 `WorkerThreadHost.cancel_enrollment()`。
2. 如果登记前正在识别，则保留当前线程并将状态恢复为 `RECOGNIZING`。
3. 如果登记前处于待机，则在清除登记会话后停止线程，并将状态恢复为 `IDLE`。
4. 最后清除 `_resume_recognition` 标志。

这样由控制器明确结束登记生命周期，不把状态清理隐含到通用的 `stop` 或 `start` 中。

## 测试

- 扩展控制器测试：从待机进入登记再完成，必须同时调用宿主的 `cancel_enrollment` 和 `stop`。
- 扩展线程宿主或集成测试：登记完成后重新启动，新 worker 不得带入旧登记会话。
- 保留原有场景：识别过程中进入登记再取消时，不停止线程，只恢复识别。
- 运行控制器、worker、Fake UI 流程定向测试以及完整测试套件。

## 非目标

- 不改变 ONNX 模型、检测阈值或识别阈值。
- 不改变成员特征库。
- 不修改登记采样、姿态或清晰度逻辑。
- 不改变主界面布局。
